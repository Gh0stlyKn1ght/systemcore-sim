## 1. Limelight Systemcore OS: release 15 is now published as prerelease

The previous 2026-09-20 source snapshot correctly recorded that the inspected Limelight README called Alpha 15 and Beta 15 unreleased. That statement is now superseded by GitHub release artifacts published on 2026-09-19:

- **Alpha hardware:** `limelightosr-2027.0.0-alpha15-382`, published 2026-09-19 03:55:55 UTC.
- **Beta hardware:** `limelightosr-2027.0.0-beta15-212`, published 2026-09-19 03:39:06 UTC.
- Both releases identify source commit `81dd853e1fd31e0b6e372018d9556840c9136435` and build date `2026-09-18T18:29:18-07:00`.
- Both expose a full image, `.llupdate` payload, aarch64 cross-compilation toolchain, kernel source archive, and license manifest.
- GitHub marks these releases as **prerelease**. The current README also warns that listed image-15 changes may not all be present until final release. Therefore “published” does not mean “final season image.”

Primary releases:
- https://github.com/LimelightVision/systemcore-os-public/releases/tag/limelightosr-2027.0.0-alpha15-382
- https://github.com/LimelightVision/systemcore-os-public/releases/tag/limelightosr-2027.0.0-beta15-212

The current Limelight changelog lists image-15 work including faster startup, Motioncore OTA behavior, lower vision/classifier memory use, corrected process-memory accounting, a camera capture-rate fix, more detailed eMMC health, and Motioncore 0.7.0/0.7.1 changes. A 2026-09-21 README commit adds a hardware-revision distinction: Beta OLEDs remain on at reduced brightness/framerate after inactivity, while Alpha OLEDs continue to turn off. These are vendor release notes, not measurements from this project.

Current changelog commit: https://github.com/LimelightVision/systemcore-os-public/commit/8783d4c40a159fd9e17458c56f5ca9e708d2e767

**Compatibility impact:** do not write “Systemcore image 15” without also recording Alpha versus Beta hardware. SystemcoreTesting currently says image `>=14` pairs with WPILib `>=2027.0.0-alpha-7`, while individual vendor notes may be narrower. A classroom image should therefore be pinned with hardware revision, image tag/build, WPILib, Driver Station, vendor library, device firmware, and configuration tool.

## 2. WPILib and SystemcoreTesting

The latest tagged WPILib release found remains **WPILib 2027.0.0 Alpha 7**, published 2026-09-01. Its release notes explicitly identify breaking changes, require Systemcore image 14, and state that Alpha 6 and earlier vendordeps do not work with Alpha 7. Notable migration items include Telemetry/Tunables replacing older SmartDashboard/Sendable APIs, a `CANPort` enum for high-level CAN device classes, nanosecond raw timestamps, SDL-based desktop GUI/gamepad handling, C++23, and further Java package moves.

Release: https://github.com/wpilibsuite/allwpilib/releases/tag/v2027.0.0-alpha-7

## 3. FIRST Driver Station alpha 8

FIRST Driver Station **v2027.0.0-alpha-8** was published 2026-09-14. It is a patch release over alpha 7 and includes Linux x64/arm64, Windows x64/arm64, and macOS assets. The release notes say it is required for SoCal Showdown and recommended for teams connected to an FMS. Fixes include simulation camera loopback, dashboard lookup, FMS behavior, display/console memory leaks, alert-key lookup, and FTA visibility into FMS UDP flow.

Release: https://github.com/wpilibsuite/FirstDriverStation-Public/releases/tag/v2027.0.0-alpha-8

GitHub's release metadata marks this tag `prerelease: false` even though the version itself is explicitly `alpha-8`. For this dossier it is classified as a **published alpha build**, not a final 2027 season release.

**Simulation/classroom implication:** the loopback-camera fix is directly relevant to desktop simulation, but no local acceptance test was run. Pin the Driver Station version independently because the WPILib alpha-7 release note names DS alpha 7 while a newer alpha-8 DS now exists.

## 4. Merged WPILib work after alpha 7 is not alpha-7 released behavior

Several relevant changes merged to `allwpilib` after the 2026-09-01 alpha-7 release:

- **2026-09-16, `813dc402...`**: adds AOS as an internal dependency and an `aosnt` bridge that publishes selected AOS channels to NetworkTables. The commit says the first target is realtime `mrccomm` control data, while dashboards continue reading ordinary NetworkTables topics. This is a Systemcore architecture development, not ROS 2.
- **2026-09-18, `e7823869...`**: adds Driver Station alerts to the simulation GUI.
- **2026-09-18, `5a659b2c...`**: displays simulation devices as a slash-separated tree.
- **2026-09-18, `8e42a614...`**: adds Java module support.
- **2026-09-18, `e199568d...`**: connects `mrclib` team number handling.
- **2026-09-16, `793da538...`**: improves RobotPy native-wheel parity but still notes remaining packaging/type-stub work.
- **2026-09-14, `d8da5256...` and `5ae4836...`**: fix NetworkTables outgoing-queue bookkeeping and subscription send-mode behavior.

Architecture source example: https://github.com/wpilibsuite/allwpilib/commit/813dc4022128119375a7a33aaa4dd4d8a85da5c1

These are **merged upstream source changes**. This review did not find a newer tagged WPILib release containing them, so they must not be represented as alpha-7 capabilities.

**Architecture implication:** the AOS bridge is evidence of internal real-time communication evolution while maintaining NetworkTables interoperability. It does not turn the documented FRC application workflow into ROS 2. Java/WPILib remains this project's primary application and classroom model.

## 5. REV Robotics and A301

The current SystemcoreTesting REV notes document:

- **REVLib `2027.0.0-alpha-7`**, matched to WPILib Alpha 7.
- CAN device constructors use WPILib `CANPort` instead of a raw integer bus ID.
- `getBusId()` becomes `getCanPort()`.
- **REV Hardware Client 2 `1.4.2`** is linked as the Systemcore arm64 IPK.
- For devices other than A301, the note says there are currently no new 2027 firmware versions and points to the latest 2026 firmware: SPARK Flex `26.1.6`, SPARK MAX `26.1.5`, and PDH, PH, Servo Hub, and MAXSpline Encoder `26.1.3`.

Source: https://github.com/wpilibsuite/SystemcoreTesting/blob/2bb26c8ee952e06b566233bbc9c2dabf79a0b04d/REV.md

For A301, the current test note links **firmware `2027.0.0-prerelease.17`**. Firmware prerelease 15 introduced a breaking A301 CAN protocol. REVLib alpha 4+ and A301 prerelease 15+ must be paired, and RHC2 must be at least 1.2.1 before that firmware transition. Prerelease 17 adds inversion configuration, individual status-frame periods, and a vendor claim that firmware survives voltage drops below 6 V.

Source: https://github.com/wpilibsuite/SystemcoreTesting/blob/2bb26c8ee952e06b566233bbc9c2dabf79a0b04d/A301.md

**Unknown:** the A301 note says native WPILib API support is planned later. That is not evidence that native WPILib A301 support is released today. Likewise, older FIRST material describing planned 2027 A301 legality is not a substitute for the final 2027 Game Manual.

## 6. CTRE

CTRE's dated 2026-09-18 changelog documents **Phoenix 6 26.70.0-alpha-2** for WPILib alpha 7 on Systemcore Alpha/Beta image 14, with **26.70.x** device firmware. It states that this alpha does not support roboRIO. The release replaces `CANBus.systemcore(int)` with `new CANBus(CANPort)`, expands bus status information, adds Telemetry/Alerts integration, and includes several Systemcore/Motioncore fixes.

CTRE also reports “up to 40%” Java native-call improvement. That is a vendor performance claim, not an independently reproduced benchmark.

**Open compatibility question:** Limelight has now published image 15 prereleases, while the checked CTRE note explicitly names image 14. SystemcoreTesting's general matrix says image `>=14`, but this review did not find a CTRE statement specifically validating image 15. Do not infer vendor-specific validation from the broader matrix.

## Compatibility snapshot for future test records

The project should now record a test profile in this shape:

```text
Hardware revision:       Alpha | Beta | production-unknown
Systemcore image:        exact tag + build
Motioncore firmware:     exact version if present
WPILib:                  exact release/tag
Driver Station:          exact release/tag
Vendor library:          exact version
Device firmware:         exact version per device
Configuration tool:      exact version
Desktop OS/architecture: exact release + arch
Robot source commit:     exact SHA
Test type:               desktop simulation | hardware bench | field
```

A single label such as “2027 alpha” is no longer precise enough.

## Project implications

### Compatibility

Treat controller image, WPILib, Driver Station, vendordep, firmware, and hardware revision as one compatibility profile. Do not assume `>=14` in a general table means every vendor has separately validated every newer image.

### Linux simulation

The current project decision remains sound: use WPILib desktop simulation on a supported host, not generic ARM OS emulation as the first target. Driver Station alpha 8's loopback-camera fix and the post-alpha7 simulation GUI work are relevant, but they need a release-matched acceptance test before becoming classroom instructions.

### Classroom

Pin a known-good semester image instead of following `main`. Student worksheets should identify whether a feature is released, merged-only, vendor-specific, or proposed. The new multi-bus and stale-signal APIs remain useful teaching material because they force students to reason about identity, validity, and version compatibility.

### Architecture

The merged AOS-to-NetworkTables bridge is the most architecture-relevant upstream change in this review. It shows a separation between internal realtime communication and the existing NetworkTables-facing dashboard/telemetry surface. This is not ROS 2 and does not change the repository's Java/WPILib application focus.

### Research

Add an image-15 compatibility pass to the future hardware test plan, but do not call it complete until a physical Alpha/Beta unit and release-matched vendor set are actually tested. Retain old issue reports with their original version and link them to vendor release-note fixes rather than marking them universally resolved.
