# Robot states and timing

**Essential question:** Which work belongs to the selected OpMode, and which work must continue for the whole robot application?

## Learning targets

By the end of this lesson, you can:

- distinguish robot-wide callbacks from selected-OpMode callbacks;
- calculate the effect of a 20-millisecond periodic interval; and
- prevent custom periodic work from issuing unsafe requests while disabled.

## Two callback scopes

The `Robot` object can receive callbacks that are independent of one selected OpMode.

| Robot-wide callback | Appropriate responsibility |
|---|---|
| `driverStationConnected()` | Record connection or publish robot-wide identity once a station connects |
| `robotPeriodic()` | Update robot-wide diagnostics used in every state |
| `disabledInit()` | Perform one quick action when the robot enters disabled |
| `disabledPeriodic()` | Repeat robot-wide disabled work |
| `disabledExit()` | Finish robot-wide disabled preparation |
| `nonePeriodic()` | Report the state when no OpMode is selected |
| `simulationInit()` | Initialize desktop-only models once |
| `simulationPeriodic()` | Advance desktop models repeatedly |

The selected `PeriodicOpMode` owns the lifecycle of one autonomous, teleoperated, or utility behavior. Do not duplicate the same responsibility in both scopes.

## The 20-millisecond budget

At the default interval:

`1 second / 0.020 seconds per call = 50 calls per second`

A ten-second enabled period contains about 500 scheduled calls. That count is an expectation, not a hard real-time guarantee. Slow work in one callback can delay later work.

Keep periodic code bounded:

- do not sleep;
- do not wait in a loop for a sensor value;
- avoid opening files or network connections every cycle;
- record elapsed time when timing matters; and
- separate a requested state from confirmation that hardware reached it.

## Custom periodic callbacks

The framework can schedule callbacks at custom rates. In the 2027 OpMode model, those callbacks can continue while the robot is disabled. Any callback that could request actuator output therefore needs an explicit enabled-state guard.

```java
addPeriodic(
    () -> {
      if (DriverStation.isEnabled()) {
        updateFastControl();
      }
    },
    0.010);
```

Treat this as the safety rule even if downstream libraries also suppress physical output. The application should express neutral intent when permission is absent.

## Independent diagnosis

A 10-millisecond callback reads an encoder and updates a motor request. The code was written while the robot was enabled, then the robot is disabled. The callback has no enabled check.

Answer all three:

1. Does the callback stop merely because the robot is disabled?
2. What should the application request while permission is absent?
3. What evidence would show whether physical output was actually suppressed?
