# Module 02: WPILib foundations

WPILib decides when robot code is called. This module makes that control flow visible before any motor, sensor, or vendor API is introduced.

## Module outcome

You will create a Java project with desktop support, identify the framework-owned and team-owned entry points, trace one OpMode from selection through cleanup, and produce a lifecycle record that another student can audit.

## The reference architecture

This course uses **Java `OpModeRobot`** for its 2027 reference path. Shared hardware and long-lived services belong to the `Robot` object. Autonomous, teleoperated, and utility behavior live in separate `PeriodicOpMode` classes.

That is a course architecture decision, not a claim that every FRC team must migrate. `TimedRobot` remains supported, and Command-based projects remain a strong choice for teams that need command composition and subsystem scheduling.

## Lifecycle at a glance

| Event | Framework action | Team callback |
|---|---|---|
| OpMode selected | Construct a fresh OpMode object | Constructor |
| Selected while disabled | Repeat at the normal loop rate | `disabledPeriodic()` |
| Robot enabled | Begin the selected behavior once | `start()` |
| Enabled loop | Repeat at the normal loop rate | `periodic()` |
| Robot disabled | Stop the active behavior | `end()`, then `close()` |
| Selection changed while disabled | Dispose of the old selection | `close()` |

The default periodic interval is 20 milliseconds, or 50 calls per second. A callback name describes when WPILib invokes code. It does not prove that physical energy has been removed.
