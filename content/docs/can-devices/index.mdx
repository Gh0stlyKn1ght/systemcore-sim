# Module 05: CAN and devices

CAN is a shared communications network. A motor controller may use CAN to receive commands and report measurements, but motor power travels through a different circuit.

## Module outcome

You will document a CAN device by full address, trace its hardware and software dependencies, classify the first unverified boundary, and diagnose a duplicate-address fault without guessing from one status light.

## Device readiness model

This module keeps eight states separate:

1. topology documented;
2. termination assumptions verified;
3. full address unique;
4. device visible in its configuration tool;
5. firmware compatible;
6. vendor dependency installed in the project;
7. Java API compatible with the selected release; and
8. ready for bounded integration.

Passing one state does not prove the next. A configuration application can see a device even when the robot project lacks its Java library. A project can compile against a library while the physical device remains on another bus.

## Executable diagnosis

The Java artifact now includes ten CAN identity and readiness checks:

```bash
npm run test:java
```

Expected result:

```text
PASS: 27 Java behavior, Driver Station, and CAN device checks
```

The model classifies prepared observations. It does not electrically test a bus, configure firmware, or communicate with a physical device.

## Systemcore note

WPILib’s 2027 changelog states that Systemcore supports multiple CAN buses. Therefore a device number alone is not a complete identity. This course records the bus, manufacturer, device type, and device number.

The general WPILib CAN wiring page still describes the older roboRIO-to-PDP topology. Use its two-wire and termination principles, but verify Systemcore connectors, bus names, and terminating hardware against current Systemcore and device documentation before wiring.
