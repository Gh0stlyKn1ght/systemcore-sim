# Layer 2: Startup and I/O support

**Essential question:** What has to become ready before a robot application can trust an input or issue an output?

## Learning targets

By the end of this lesson, you can:

- distinguish power-on, imaging, deployment, and device-firmware updates;
- explain why application startup does not guarantee sensor readiness; and
- design an explicit readiness state instead of trusting a default number.

## Responsibility

This layer prepares the platform and its specialized I/O resources so the operating environment and robot application can use them.

| roboRIO | Systemcore |
|---|---|
| Boot support starts the controller platform | Platform startup initializes the CM5-based controller |
| FPGA configuration establishes supported hardware logic | RP2350 firmware and platform support establish specialized I/O behavior |
| Controller image and FPGA behavior belong to the platform | Controller image, services, packages, and peripheral firmware must be compatible |

The team’s Java class is not FPGA configuration and it is not RP2350 firmware.

## Three operations students must not merge

**Power-on** starts the installed platform. **Imaging** installs or replaces controller system software. **Deploying** builds and transfers the team application. External device firmware is a fourth versioned concern.

```text
Power usable
  -> startup firmware and hardware initialization
  -> operating environment and drivers
  -> controller services and I/O support
  -> installed robot application
  -> operator connectivity and mode state
```

This is a responsibility sequence, not a measured timing trace. Several operations can overlap.

## Test boundary

Desktop simulation can model “I/O ready” and “I/O unavailable” states. It cannot validate the real controller’s startup timing, firmware recovery, image compatibility, or electrical readiness.

## Failure exercise

Model a sensor that is unavailable during application startup and becomes available later. The application must report readiness explicitly rather than interpreting a default numeric value as a valid measurement.

Use a state model such as:

```text
UNAVAILABLE -> INITIALIZING -> READY
                     \-> FAULT
```

The numeric measurement and the readiness state answer different questions. A value of `0.0` can be a real measurement, an initialization default, or a failure symptom.

## Guided investigation

For each action, identify what it changes:

| Action | Platform image | Team application | External device firmware |
|---|---:|---:|---:|
| Deploy Java robot code | No | Yes | No |
| Reimage the controller | Yes | May remove or require redeployment | No |
| Update one motor controller | No | No | Yes |
| Restart robot code | No | Restarts the process | No |

## Independent diagnosis

The controller is reachable, the application started, and the gyro reports `0.0` forever. Write three competing explanations that belong to different layers. Then name the next observation that would separate them.

## Exit ticket

Why is “the application started” weaker evidence than “the sensor is ready and its timestamp is advancing”?
