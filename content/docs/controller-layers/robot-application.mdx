# Layer 6: Robot application

**Essential question:** How do we turn an operator request and sensor observations into a bounded, explainable robot action?

## Learning targets

By the end of this lesson, you can:

- write a behavior as observations, decision, request, and telemetry;
- define a neutral fallback for invalid input or missing permission; and
- place build, unit-test, simulation, telemetry, and hardware evidence in the correct order.

## 42-minute plan

| Minutes | Work |
|---|---|
| 0–4 | Write the rule your robot should follow when input becomes invalid. |
| 4–14 | Map observations, intent, decisions, and output requests. |
| 14–26 | Convert one requirement into Java-like pseudocode. |
| 26–36 | Test the rule against normal, disabled, and stale-input cases. |
| 36–42 | Complete the exit ticket and identify the next stronger evidence. |

## Responsibility

This is the behavior the team writes: driving, mechanisms, autonomous routines, interlocks, diagnostics, and fallback decisions.

The application receives observations and operating state, decides what should happen, and produces bounded requests. It should not hide hardware access throughout unrelated classes.

```text
observations + mode + operator intent
                -> behavior decision
                -> output request + telemetry
```

## First Java milestone

The initial implementation will contain:

- differential-drive manual control;
- one short autonomous routine;
- simulated encoder and heading inputs;
- JUnit tests for behavior decisions;
- WPILib desktop simulation;
- useful telemetry for inputs, decisions, and outputs;
- one stale-sensor scenario with a defined fallback.

## Required test progression

1. **Build:** the project and dependencies assemble.
2. **Unit test:** decision logic satisfies named requirements.
3. **Simulation:** integrated behavior operates against a software model.
4. **Telemetry review:** another person can explain why the result occurred.
5. **Hardware validation:** a bounded bench test checks assumptions that software cannot prove.

## Example requirements

- Zero joystick input produces a neutral drive request.
- Canceling autonomous produces a stopped output request.
- Disabled-state input cannot produce an active application output request.
- An observation older than the accepted threshold triggers the documented fallback.

## Completion rule

A clean checkout must build, discover and run its tests, launch the selected simulation, expose understandable telemetry, reproduce one deliberate fault, and return to the known-good baseline.

Only then should we add vendor-specific hardware integration, swerve drive, multiple cameras, or a second mechanism.

## Requirement to decision

Start with plain language:

> When teleop is enabled and the drive input is fresh, calculate a bounded drive request. Otherwise request neutral output.

Then make every condition visible:

```java
if (!mode.teleopEnabled() || !driverInput.fresh()) {
  return DriveRequest.neutral();
}

return DriveRequest.arcade(
    clamp(driverInput.forward()),
    clamp(driverInput.turn())
);
```

The real implementation will use the selected WPILib APIs and project structure. This pseudocode exists to expose the rule before framework details are added.

## Independent diagnosis

The simulation moves correctly, but the telemetry records no input timestamp and no selected fallback reason. Decide whether the behavior is ready for a fault exercise. Defend your answer using the evidence ladder.

## Exit ticket

Write one requirement for neutral output that can be tested without a robot. Include the input condition and the expected request.
